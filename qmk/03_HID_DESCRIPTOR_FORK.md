# 03 — HID Descriptor Fork (3Dconnexion Multi-Axis Controller)

The single hard blocker in this port. Everything else is ordinary QMK work.

---

## 1. The problem

3DxWare (the 3Dconnexion driver that Fusion 360, SolidWorks, Inventor etc. talk to) binds a
device by **VID/PID *and* HID descriptor structure**. It requires:

| Requirement | Stock QMK |
|---|---|
| Top-level usage = **Multi-axis Controller (0x08)** | ❌ hardcoded to Joystick (0x04) |
| Report ID 1 = translation X/Y/Z, 3× int16 | ❌ single combined report, no report IDs |
| Report ID 2 = rotation Rx/Ry/Rz, 3× int16 | ❌ |
| Report ID 3 = 32 buttons | ❌ buttons in the same report as axes |
| VID/PID `0x256F:0xC631` | ✅ `keyboard.json` |

QMK builds all HID descriptors as compile-time `PROGMEM` arrays in
`tmk_core/protocol/usb_descriptor.c`, gated by feature `#ifdef`s. **There is no hook for a
keyboard to supply its own HID interface** — no weak symbol, no `_kb` override, nothing. I
checked: the only keyboard-configurable descriptor knobs are `RAW_USAGE_PAGE` /
`RAW_USAGE_ID`, and Raw HID's report body is a flat 32-byte vendor array with no axis usages
and no report IDs, so 3DxWare will not bind to it.

**Therefore: a small fork of the QMK core is required.** This was the conclusion of the
original feasibility study and it is confirmed.

---

## 2. Scope of the patch

4 files, well under 200 lines changed. Maintained as a branch on our QMK fork, rebased onto
release tags.

| File | Change |
|---|---|
| `tmk_core/protocol/usb_descriptor.c` | Replace the joystick HID report descriptor with the multi-axis version |
| `tmk_core/protocol/usb_descriptor.h` | Adjust `JOYSTICK_EPSIZE` if needed |
| `tmk_core/protocol/report.h` | Add the three report structs |
| `tmk_core/protocol/lufa/lufa.c` | Split `send_joystick()` into 3 report writes |

Gate everything behind a new define so the patch is inert for every other keyboard:

```c
#ifdef JOYSTICK_MULTIAXIS_ENABLE
   ... new descriptor ...
#else
   ... stock joystick descriptor ...
#endif
```

Set `#define JOYSTICK_MULTIAXIS_ENABLE` in our `config.h`. This makes the fork safe to
rebase and, in principle, upstreamable later.

---

## 3. The descriptor, in QMK's `HID_RI_*` macro style

Direct transliteration of `orbit_hid_descriptors.h` (Inventory §2.1). QMK uses LUFA's
`HID_RI_*` macros where the first argument is the data size in bits.

```c
#ifdef JOYSTICK_MULTIAXIS_ENABLE
const USB_Descriptor_HIDReport_Datatype_t PROGMEM JoystickReport[] = {
    HID_RI_USAGE_PAGE(8, 0x01),             // Generic Desktop
    HID_RI_USAGE(8, 0x08),                  // Multi-axis Controller
    HID_RI_COLLECTION(8, 0x01),             // Application

        // ---- Report ID 1: Translation ----
        HID_RI_COLLECTION(8, 0x00),         // Physical
            HID_RI_REPORT_ID(8, 0x01),
            HID_RI_LOGICAL_MINIMUM(16, -32768),
            HID_RI_LOGICAL_MAXIMUM(16, 32767),
            HID_RI_PHYSICAL_MINIMUM(16, -32768),
            HID_RI_PHYSICAL_MAXIMUM(16, 32767),
            HID_RI_USAGE(8, 0x30),          // X
            HID_RI_USAGE(8, 0x31),          // Y
            HID_RI_USAGE(8, 0x32),          // Z
            HID_RI_REPORT_SIZE(8, 16),
            HID_RI_REPORT_COUNT(8, 3),
            HID_RI_INPUT(8, HID_IOF_DATA | HID_IOF_VARIABLE | HID_IOF_ABSOLUTE),
        HID_RI_END_COLLECTION(0),

        // ---- Report ID 2: Rotation ----
        HID_RI_COLLECTION(8, 0x00),         // Physical
            HID_RI_REPORT_ID(8, 0x02),
            HID_RI_LOGICAL_MINIMUM(16, -32768),
            HID_RI_LOGICAL_MAXIMUM(16, 32767),
            HID_RI_PHYSICAL_MINIMUM(16, -32768),
            HID_RI_PHYSICAL_MAXIMUM(16, 32767),
            HID_RI_USAGE(8, 0x33),          // Rx
            HID_RI_USAGE(8, 0x34),          // Ry
            HID_RI_USAGE(8, 0x35),          // Rz
            HID_RI_REPORT_SIZE(8, 16),
            HID_RI_REPORT_COUNT(8, 3),
            HID_RI_INPUT(8, HID_IOF_DATA | HID_IOF_VARIABLE | HID_IOF_ABSOLUTE),
        HID_RI_END_COLLECTION(0),

        // ---- Report ID 3: 32 buttons ----
        HID_RI_COLLECTION(8, 0x00),         // Physical
            HID_RI_REPORT_ID(8, 0x03),
            HID_RI_LOGICAL_MINIMUM(8, 0x00),
            HID_RI_LOGICAL_MAXIMUM(8, 0x01),
            HID_RI_REPORT_SIZE(8, 1),
            HID_RI_REPORT_COUNT(8, 32),
            HID_RI_USAGE_PAGE(8, 0x09),     // Button
            HID_RI_USAGE_MINIMUM(8, 1),
            HID_RI_USAGE_MAXIMUM(8, 32),
            HID_RI_INPUT(8, HID_IOF_DATA | HID_IOF_VARIABLE | HID_IOF_ABSOLUTE),
        HID_RI_END_COLLECTION(0),

    HID_RI_END_COLLECTION(0),
};
#else
   /* ... stock QMK joystick descriptor, unchanged ... */
#endif
```

### Byte-exactness

The generated bytes must match the Arduino descriptor. Two things to watch:

1. **Item ordering inside each collection.** In the Arduino descriptor the logical/physical
   min/max come *before* the usages; in the button collection the usage page comes *after*
   report size/count. HID parsers are order-sensitive for global vs. local items. The macro
   order above mirrors the Arduino array exactly — keep it.
2. `HID_RI_LOGICAL_MINIMUM(16, -32768)` emits `0x16, 0x00, 0x80` ✓ and
   `HID_RI_LOGICAL_MAXIMUM(16, 32767)` emits `0x26, 0xFF, 0x7F` ✓.

**Verification step:** dump the descriptor from both the Arduino firmware and the QMK build
(`usbhid-dump` on Linux, USB Device Tree Viewer on Windows, or `lsusb -vd 256f:c631`) and
`diff` the hex. They must be identical. This is a mandatory gate in the task list.

## 4. Report structs (`report.h`)

```c
#ifdef JOYSTICK_MULTIAXIS_ENABLE
#    define REPORT_ID_MULTIAXIS_TRANS  1
#    define REPORT_ID_MULTIAXIS_ROT    2
#    define REPORT_ID_MULTIAXIS_BTN    3

typedef struct {
    uint8_t report_id;
    int16_t x;
    int16_t y;
    int16_t z;
} __attribute__((packed)) report_multiaxis_trans_t;   // 7 bytes

typedef struct {
    uint8_t report_id;
    int16_t rx;
    int16_t ry;
    int16_t rz;
} __attribute__((packed)) report_multiaxis_rot_t;     // 7 bytes

typedef struct {
    uint8_t  report_id;
    uint32_t buttons;
} __attribute__((packed)) report_multiaxis_btn_t;     // 5 bytes
#endif
```

`__attribute__((packed))` is essential — without it AVR-GCC would not add padding here
anyway, but being explicit protects against ABI surprises.

`JOYSTICK_EPSIZE` must be ≥ 7. Stock is 8, so no change needed.

## 5. The send function (`lufa.c`)

Stock `send_joystick()` writes one report. Replace with three sequential endpoint writes,
mirroring the Arduino `sendCommand()` / `sendButtons()` pattern:

```c
#ifdef JOYSTICK_MULTIAXIS_ENABLE
void send_multiaxis(int16_t x, int16_t y, int16_t z,
                    int16_t rx, int16_t ry, int16_t rz) {
    report_multiaxis_trans_t t = {
        .report_id = REPORT_ID_MULTIAXIS_TRANS, .x = x, .y = y, .z = z };
    report_multiaxis_rot_t r = {
        .report_id = REPORT_ID_MULTIAXIS_ROT, .rx = rx, .ry = ry, .rz = rz };

    // Report 1 (translation) first, then Report 2 (rotation) — matches the
    // Arduino firmware's ordering, which 3DxWare expects.
    usb_endpoint_interrupt_send(JOYSTICK_IN_EPNUM, &t, sizeof(t));
    usb_endpoint_interrupt_send(JOYSTICK_IN_EPNUM, &r, sizeof(r));
}

void send_multiaxis_buttons(uint32_t buttons) {
    report_multiaxis_btn_t b = {
        .report_id = REPORT_ID_MULTIAXIS_BTN, .buttons = buttons };
    usb_endpoint_interrupt_send(JOYSTICK_IN_EPNUM, &b, sizeof(b));
}
#endif
```

Use whatever the actual helper in this QMK version is named — in 0.33.x the joystick path
selects the endpoint then does a `Endpoint_Write_Stream_LE()` + `Endpoint_ClearIN()` inside a
`Endpoint_IsReadWriteAllowed()` guard. Copy the surrounding boilerplate from the existing
`send_joystick()` verbatim; only the payload and the number of writes change.

### Two subtleties

1. **Back-to-back writes on one endpoint.** Reports 1 and 2 go out on the same interrupt
   endpoint in the same scan. The second write must wait for the first to be consumed —
   the existing `send_joystick()` boilerplate already handles the
   `Endpoint_IsINReady()`/timeout dance; reuse it per write. Do not fire and forget.
2. **Button report is only sent on change** in the QMK port, whereas the Arduino version
   sends it every loop. Sending unconditionally is simpler and matches the original exactly;
   given we have endpoint bandwidth to spare, **send unconditionally** to preserve behavior.

`quantum/joystick.c` should have its axis/button plumbing bypassed entirely for our keyboard
— we call `send_multiaxis()` directly from `orbit_6dof.c` rather than going through
`joystick_set_axis()` + `joystick_flush()`. The joystick feature is enabled only to get the
interface + endpoint allocated.

## 6. Endpoint budget

ATmega32U4: EP0 control + **6 usable**. QMK enforces this at compile time in
`usb_descriptor.h` (`#error There are not enough available endpoints`).

| Interface | Endpoints |
|---|---|
| Keyboard + Mouse shared (`KEYBOARD_SHARED_EP` + `MOUSE_SHARED_EP`) | 1 |
| Joystick → multi-axis | 1 |
| Raw HID (VIA) | 2 (IN + OUT) |
| **Total shipping build** | **4 of 6** ✅ |
| + Console (debug builds) | 5 of 6 ✅ |

Comfortable. Endpoints were never the constraint.

## 7. Host-side validation matrix

| Host | Driver | Expected |
|---|---|---|
| Windows + 3DxWare | 3Dconnexion | Device appears as SpaceMouse Pro Wireless; all 6 axes + buttons in the 3Dconnexion control panel |
| Windows, no driver | HID | Appears as a generic multi-axis controller |
| macOS + 3DxWare | 3Dconnexion | Same as Windows |
| Linux + spacenavd | free driver | Binds by ID; `spnavtest` shows all 6 axes |
| Fusion 360 | via 3DxWare | Orbit/pan/zoom works identically to the Arduino firmware |
| Blender | native/spacenavd | 6DOF navigation works |

The acceptance bar: **a user cannot tell the QMK firmware from the Arduino firmware** in any
of these environments.

## 8. Fork maintenance

```
qmk_firmware (our fork)
├── master                        ← tracks upstream
└── hackman3d/multiaxis           ← the patch, rebased onto release tags
```

The patch touches 4 files in `tmk_core/protocol/`, an area that changes rarely. Expect a
rebase roughly yearly. Keep the patch as a single squashed commit so `git rebase` conflicts
are trivial to resolve, and keep the `JOYSTICK_MULTIAXIS_ENABLE` gate so the diff is purely
additive.

Also worth doing: generate the patch as a `.patch` file checked into this docs repo
(`qmk/patches/0001-multiaxis-hid.patch`) so the port is reproducible from a clean upstream
QMK clone without needing access to the fork.
